Overview

Collect six step-response datasets per team: three parameter configurations × two control channels.

Configuration Speed (throttle) Yaw rate (steering)
Base <FILE1>.BIN <FILE2>.BIN
FeedForward <FILE3>.BIN <FILE4>.BIN
Tuned <FILE5>.BIN <FILE6>.BIN

Plan for two field sessions. The first session typically surfaces issues (vehicle setup, parameter staging, pilot/scribe rhythm) that need fixing on a second day.

Read this whole page before the first field session. The goal is to understand what we are accomplishing by working through the procedural steps. The ArduPilot autopilot is a complex system with many parameters and scant documentation, and the post-processing relies entirely on the scribe’s notes to navigate dozens of .mat files. It is tough to see the trees, let alone the forest.

1. Pre-lab preparation

1.1 Day before

  • Rotate roles among team members to ensure everyone understands each responsibility.
    • For each role (planner, pilot, scribe) ensure that someone is familiar with the responsibilities and tasks associated with that role. Good idea to get some training from your predecessor before the field session. The goal of doing this rotation is to share the hands-on experience and understanding among all team members.
  • Hardware prep — it is a shared responsibility to ensure your team has everything to be successful.
    • Collect: Boat, 900 MHz radio, R/C transmitter, ground laptop (with Mission Planner). Make sure they are in one place and ready to transport to the field.
    • Charge: Batteries for vehicle propulsion, autopilot, R/C transmitter, ground laptop.
  • “Print”: Test log — one row per dataset (six total) for parameter values, observations. Template. This is just a template; students can make their own version if they want, but the key is to have a structured place to record the UTC timestamp and intent for each arm event, which is how the resulting .mat files get navigated during post-processing.

1.2 Day of

  • Parameter files staged on the laptop. You are given the baseline .param for the Base experiment. The planner will be responsible for loading the appropriate parameter files for each experiment and ensuring they are correctly applied to the autopilot.
  • If using scripted steps, stage the script on the laptop. Download the step-input script and review the script setup.
  • Roles:
    • Planner — drives Mission Planner: monitors ARM and mode state (MANUAL, ACRO), modifies parameters between experiments, sets up real-time displays, and runs the step-input script if that method is chosen.
    • Scribe — keeps the test log and records UTC time + intent at every arming event. The scribe’s notes are what makes the resulting tens of .mat files navigable during post-processing.
    • Pilot — drives the boat with the RC transmitter and applies the steps if the manual method is chosen. For scripted speed steps, keeps the physical throttle at neutral; for scripted yaw-rate steps, holds steady throttle and keeps the physical steering stick centered.

2. Shore setup

As in Lab 1, confirm the following at the launch site before any data collection.

  • Safety. Stay clear of the propellers whenever the boat’s propulsion battery is connected.
  • SD card in the autopilot.
  • Power on the autopilot.
  • Establish telemetry link with Mission Planner.
  • Load the baseline .param file and confirm the relevant ATC_* parameters are at the expected values. In particular, verify ATC_ACCEL_MAX = 0 and ATC_STR_ACC_MAX = 0 so that step inputs reach the loops as true steps. ATC = Attitude Control, see Ardu Common Abbreviations. See the Stabilization Layer reference for what each parameter does.
  • Verify the throttle and steering RC input channels. In Mission Planner’s Radio Calibration display, move only the throttle stick and identify the responding channel, then move only the steering stick and identify its channel. Record both channel numbers, their neutral PWM values, and which stick direction increases or decreases PWM. These are RC input channels, not servo-output channel numbers. Channel 3 for throttle and Channel 1 for steering are examples to verify, not assumed assignments. Use the verified input channel when setting the script’s CHANNEL for each trial.
  • If using the step-input script, check RC_OVERRIDE_TIME in the Full Parameter Tree. It should be a small positive value (ArduRover default 3 s), so an override expires if the telemetry link or Mission Planner drops. A value of -1 means overrides never time out; do not run the script with that setting.
  • Power on the propulsion system.
  • Confirm ARM and that you can switch from MANUAL to ACRO modes.
  • You may need to re-bind the RC transmitter and/or calibrate sensors.

3. Experiments

The lab cycles through three experiments, applying the same procedure to each. Only the parameter set changes between cases (see §3.3 for the per-experiment delta):

  1. Base — ArduRover default PID gains; no feedforward; rate limiters off.
  2. FeedForward — same PID gains as Base, with the Lab 1 sysid feedforward added (ATC_*_FF = 1/K_dc).
  3. Tuned — keep the FeedForward configuration, then iterate on ATC_*_P/I/D for “best” response.

3.1 ARM and logging

The autopilot starts a new log file every time the pilot arms it. Treat each arm-disarm cycle as one experimental purpose: one cycle for the speed step trials, one for the yaw-rate trials. This keeps each .mat file scoped to a single channel, which makes the MATLAB time-series easier to inspect. Expect to accumulate dozens of .mat files over a session; the scribe’s notes (UTC time with seconds plus a brief intent description at every arm) are how you map each .mat back to what was being tested. The post-processed .mat filename includes the UTC timestamp.

3.2 Procedure for each experiment

Run the following sequence three times, once per experiment (Base → FeedForward → Tuned).

For each channel, choose one of two optional methods: Option 1 — manual stick input, or Option 2 — Mission Planner script input. Both methods use the same ACRO-mode confirmation and arm-disarm logging cycle. Keep the chosen step amplitude consistent across Base, FeedForward, and Tuned.

Set up the experiment

  1. Change the parameter set for this experiment via Mission Planner (Config → Full Parameter Tree). For Base, load the baseline .param. For FeedForward and Tuned, you will be changing the relevant ATC_* parameters as specified in the lab instructions.

  2. Verify the relevant ATC_* parameters at the vehicle. Mission Planner shows live values; see the Stabilization Layer reference for what each parameter does and which ones change between experiments.

Step-input script (for Option 2)

Download step_input.py, or copy the code below into a plain-text file with that name. Edit and save the three student settings before each type of trial. This script runs inside Mission Planner, which supplies the Script object.

# Step input for ME2801 Lab 2. Runs inside Mission Planner (DATA -> Scripts),
# which supplies the Script object. It will not run from a normal Python prompt.
import time

# Student settings
DURATION_SECONDS = 30
CHANNEL = 3
PWM = 1550

# Start timer
end_time = time.time() + DURATION_SECONDS
print("Step start: channel %d at %d PWM for %d s" % (CHANNEL, PWM, DURATION_SECONDS))

try:
    while time.time() < end_time:
        Script.SendRC(CHANNEL, PWM, True)
        Script.Sleep(100)

finally:
    # Release RC override (0 = return channel to the transmitter)
    Script.SendRC(CHANNEL, 0, True)
    print("Step end: channel %d released" % CHANNEL)
  • DURATION_SECONDS — starts at 30 seconds. The response needs to settle with at least 3 seconds of steady data before the step ends; extend the duration for a subsequent trial if needed.
  • CHANNEL — set this to the verified RC input channel for the trial: throttle for speed, steering for yaw rate. The default 3 is only an example for throttle; likewise, verify rather than assume 1 for steering.
  • PWM — start speed trials at 1550. Adjust as needed to obtain a clear response below planing speed, then reuse the chosen PWM across experiments. For yaw-rate trials, choose a steering PWM and direction using the verified calibration; the speed starting value is not a steering setting.

In Mission Planner, open DATA / Flight Data → Scripts, in the lower-left panel beneath the HUD. Click Select Script and choose your saved .py file. Click Run Script when the pilot and planner are ready for the step, as described below; the command starts immediately. For background, see Using Python Scripts in Mission Planner.

The loop repeatedly sends a MAVLink RC_CHANNELS_OVERRIDE command, with a 100 ms pause between sends, to hold the selected input for the specified duration. The finally block sends PWM 0 to release the override back to the physical transmitter. This is different from sending a neutral PWM (often around 1500), which still overrides the channel. The script commands one channel; the pilot controls the other channel.

RC override behavior. While an override is active, the physical stick on that channel is ignored until the override is released. Use only the verified throttle or steering input channel and keep the mode-switch channel under pilot control. Switching to MANUAL does not itself clear an RC override.

To abort a scripted step: the pilot switches to HOLD (the mode switch is never overridden), and the planner clicks Abort Script. Do not rely on a stick disarm while the throttle channel is overridden, because the stick gesture may not register. If Mission Planner stops sending, the autopilot drops the override on its own after RC_OVERRIDE_TIME seconds.

Speed (throttle) step run — one arm-disarm cycle

  1. Pilot brings the USV to open water and to rest.
  2. Pilot disarms and re-arms (closes the previous log, opens a new one). Scribe records UTC time + intent (e.g. “Base, surge step”). The full parameter set is captured inside each log, so there’s no need to save it separately.
  3. Pilot switches the autopilot into ACRO mode. Planner confirms ACRO in Mission Planner before the pilot proceeds.
  4. Repeat 1–2 times, using either Option 1 or Option 2 below. Allow the boat to return fully to rest between steps.
  5. Pilot disarms to close the log file.

You will likely need to do this a few times to get a clean step response logged.

Option 1: Manual stick input (speed)
  • Pilot applies a step throttle command. Start with a small stick deflection and adjust as needed to obtain a clear response below planing speed. Use the R/C transmitter’s display to record a numerical value and keep the amplitude consistent across Base, FeedForward, and Tuned.
  • Hold for 20–30 s so the speed response settles into a clear steady value, including at least 3 seconds beyond apparent settling. Extend the hold if needed.
  • Scribe records the step amplitude and duration.
  • Pilot returns throttle to zero. Wait at least 3 seconds beyond when the boat appears stopped before the next repeat.
Option 2: Mission Planner script input (speed)

In ACRO, the overridden throttle input is the speed setpoint rather than a direct actuator command. Reusing the same PWM gives a repeatable step amplitude across the three experiments.

  • Planner sets CHANNEL to the verified throttle RC input channel, PWM = 1550 for the starting trial, and DURATION_SECONDS = 30. Save the file and select it using the script setup.
  • Pilot holds the physical throttle at neutral throughout the scripted step, so that releasing the override returns the speed command to zero. Pilot maintains heading with the steering stick as needed.
  • With the vehicle armed and ACRO confirmed (steps 4–5), planner clicks Run Script. Scribe records the channel, PWM, duration, and step time.
  • Wait for the script to finish and release the throttle override. Verify that throttle control has returned to the pilot and allow the boat to come fully to rest, including 3 seconds beyond apparent settling, before the next repeat.
  • If the starting PWM gives too little response, adjust it for a subsequent trial while staying below planing speed. Keep the selected PWM and duration consistent across Base, FeedForward, and Tuned, and confirm the response has at least 3 seconds of settled data before the script ends.
  • Confirm the override is released before the pilot disarms (step 7).

Yaw-rate (steering) step run — one arm-disarm cycle

  1. Pilot positions the boat in open water.
  2. Pilot disarms and re-arms. Scribe records UTC time + intent (e.g. “Base, yaw step”).
  3. Pilot switches the autopilot into ACRO mode. Planner confirms ACRO.
  4. Pilot establishes a low, approximately constant surge speed below planing speed. Perform one steering step using either Option 1 or Option 2 below while maintaining steady throttle.
  5. Pilot disarms to close the yaw-trial log.

You will likely need to do this a few times to get a clean step response logged.

Option 1: Manual stick input (yaw rate)
  • While holding steady throttle, pilot applies a step steering command at roughly 50% rudder. Use the R/C transmitter’s display to record a numerical value and keep the amplitude and direction consistent across Base, FeedForward, and Tuned.
  • Hold until the yaw rate settles, including at least 3 seconds beyond apparent settling.
  • Scribe records the surge speed, step amplitude, duration, and direction.
  • Pilot returns steering to center and waits for the yaw rate to return to its baseline before disarming (step 12).
Option 2: Mission Planner script input (yaw rate)

Use the same step-input script with the verified steering RC input channel. In ACRO this input commands the yaw-rate setpoint, scaled by ACRO_TURN_RATE. Only steering is overridden; the pilot holds steady throttle throughout the trial.

  • Planner changes CHANNEL from the speed-trial setting to the verified steering channel (Channel 1 is only an example). Choose PWM for the desired steering amplitude and direction from the Radio Calibration readings, and start with DURATION_SECONDS = 30. Save the file and select it in Mission Planner.
  • After arming and confirming ACRO (steps 9–10), pilot holds a steady throttle that produces a low, constant forward speed. Allow approximately 10–15 seconds to establish that speed before the steering step.
  • Pilot keeps the physical steering stick centered throughout the scripted step, so that releasing the override returns steering to center.
  • Planner clicks Run Script. Scribe records the surge speed, steering channel, PWM, duration, direction, and step time.
  • Wait for the script to finish and release the steering override. Verify steering control has returned to the pilot and wait for the yaw rate to return to its baseline before disarming (step 12).
  • Confirm the response has at least 3 seconds of settled data before the script ends; extend the duration for a subsequent trial if needed. Keep the chosen steering PWM, direction, duration, and forward-speed condition consistent across experiments.

For either method, adjust the starting amplitude for your boat and the water conditions to get a clean trace, then keep it consistent across Base, FeedForward, and Tuned.

3.3 What changes between experiments

Experiment Parameter changes from previous Notes
Base Lab preset configuration; ArduRover stock PID gains; FF off; rate limiters off; throttle baseline off First case — fully load the lab baseline .param
FeedForward Set ATC_SPEED_FF and ATC_STR_RAT_FF to 1/K_dc from the Lab 1 plant models (see below). Same PID gains as Base.
Tuned Adjust ATC_SPEED_P/I/D and ATC_STR_RAT_P/I/D for best response. FF kept on (from FeedForward). Use Mission Planner’s real-time tuning graphs to iterate on candidate gains; only execute the full arm-disarm logging cycle (steps 3–12) for the gain values you decide to keep.

Setting the feedforward gains (FeedForward and Tuned experiments)

Set each channel’s feedforward gain to 1 / K_dc, where K_dc is the DC gain of that channel’s plant model from Lab 1:

  • Speed: G_speed(s) = 5.1 / (1.3 s + 1) → ATC_SPEED_FF = 1/5.1 ≈ 0.20
  • Yaw rate: G_yaw(s) = 0.82 / (0.51 s + 1) → ATC_STR_RAT_FF = 1/0.82 ≈ 1.22

Consider the feedforward term as the amount of input the plant requires to achieve an output of 1.0. So this is the throttle command that would result in a speed of roughly 1 m/s or the rudder command that would result in a yaw rate of roughly 1 rad/s.

3.4 Tuning the PID gains (Tuned experiment)

The Tuned experiment is iterative: try a candidate set of P / I / D gains, watch how the system responds in real time, adjust, repeat. Mission Planner is the primary instrument for this — its real-time tuning graphs let you see the response without going through the field-quality-check loop for every iteration.

The ArduRover docs page Tuning Speed and Throttle (the Desired Speed to Throttle PID Tuning section) is the canonical reference. The same general approach applies to the yaw-rate channel — there isn’t a parallel docs page for it, but the workflow is the same:

  1. Start from the FeedForward configuration. P, I, D at Base values; FF at 1/K_dc. The boat should already track the target reasonably well.
  2. Open Mission Planner’s real-time tuning graphs (Flight Data → Tuning checkbox). Plot the desired vs measured signal for the channel you’re tuning.
  3. One gain at a time, small steps. Increase P first (faster response, more overshoot). If overshoot is excessive, back off P or add a small amount of D. If the steady-state error is non-zero after the FF contribution, increase I.
  4. Don’t log every iteration. Watching the real-time graphs is enough during the iteration. Only when you’ve settled on a candidate gain set worth keeping, run the full arm-disarm logging cycle (steps 3–12 of §3.2) so you have a clean .mat file with the parameter snapshot for the post-processing.
  5. Stop when “good enough.” A perfect tune is rare in one field session. Aim for a noticeable improvement in rise time and settling vs the FeedForward case, with overshoot still controlled.

3.5 Common gotchas

  • Don’t change parameters while ARMed. Parameter changes get baked into the active log in a way that makes it hard to verify what was active when. Disarm, change, save the new param file, then re-arm.
  • Verify ACRO mode every time. A test in MANUAL looks identical to one in ACRO from the pilot’s perspective, but the closed-loop controllers aren’t engaged. The planner’s ACRO confirmation in step 5 / step 10 is the safety net; don’t skip it.
  • Inter-step gap too short. Between repeats within a run, allow the response to fully settle (return to rest, or to baseline yaw rate) before the next step. A short gap mixes one step’s tail into the next step’s start.
  • Same step fraction across Base / FeedForward / Tuned. Comparing rise time, overshoot, and steady-state error across experiments should be done using equivalent amplitude step inputs for the tests. If the pilot is setting the amplitude, try to be consistent with command amplitude across the three test cases. The optional script method makes this easy: reuse the same override PWM values.
  • One channel per arm-disarm cycle. Don’t intermingle speed and yaw steps in the same log; it makes the MATLAB inspection harder than it needs to be.
  • Two timezones. ArduPilot logs and the post-processed .mat filenames are in UTC. Scribe notes are in local time. The post-processing step adds the UTC stamp to the filename automatically; the scribe should record UTC at the field too so the two match without arithmetic later. Instructors use the UTC format YYYYMMDD_HHMMSS for the appended timestamp.

4. End-of-day

Wrap up the field session.

  • Upload raw .BIN logs to the shared data repository (ME2801_USV_Shared). Add a subfolder for your team (e.g. TeamX) and put everything there:
    • the raw .BIN files (instructors will convert to .mat);
    • the scribe’s notes / test card;
    • any photos or other field-session materials.
  • Disconnect all batteries.
  • Drain the boat, put batteries on chargers, and stow the vehicle with the rest of the team’s lab materials (boat, 900 MHz radio, R/C transmitter).

5. Post-processing and quality check

The quality-check step can’t happen until the .BIN logs have been converted to .mat, which is run from the command line.

  1. Convert .BIN files to .mat. Work with the instructors to run bin2mat.py on the uploaded files. The resulting .mat files are what the MATLAB analysis scripts expect, and the UTC timestamp in each filename matches the scribe’s notes.
  2. Inspect experiment files
    • There are two important things to verify
      • That the scribe logs for the time of the pertinent experiment match the .mat file timestamps.
      • That the timeseries in the .mat file look like a clean step response with the characteristics needed to evaluate the performance metrics (rise time, overshoot, settling time, steady-state error).
    • Verify you can run the closedloop_assess_example.m as-is, then adapt it to your own log filename and run it once per .mat file.
      • The script produces the timeseries and PID-internals figures and computes step-response metrics. Suggested order is to run it across all six experiment-channel .mat files first, just to confirm each captured a clean step response.
    • Suggested characteristics to quickly verify:
      • There are no missing signals in the plots, compared with the example. Missing signals could be a mistake in the autopilot logging configuration.
      • Setpoint reaches a reasonable commanded value - consistent with the scribe logs.
      • Values all achieve a “steady state” within the duration of the step inputs.
      • No long gaps in the timeseries
