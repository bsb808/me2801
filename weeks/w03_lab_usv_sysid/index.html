Lab 1 — USV System Identification

Week 4 · Fall 2026

Objectives

In order to design and assess feedback control for the USV, it is necessary to have useful models of the vessel’s dynamics. We will use these models to predict the system’s response to control inputs and to tune the feedback controllers effectively. During this lab we will:

  • Assemble and verify the USV’s hardware and software setup.
  • Collect open-loop step response data for the surge (throttle → speed) and yaw (steering → yaw rate) channels.
  • Analyze the collected data to identify transfer function models for the surge and yaw channels.

Model Structure

There are a variety of possible model structures for the USV’s dynamics, ranging from simple first-order systems to more complex higher-order models or learned black-box models. As is often the case, simple models have advantages - they are simpler for a designer to extract intuition, they afford experimental identification (finding model parameters) more straightforwardly, and they allow for a larger set of control strategies to be applied effectively. Counter intuitively, even though the true dynamics may be more complex, simple models are often more productive at the design stage, because the control algorithm must be designed with the fact in mind that “all models are wrong, but some are useful.”

For this reason, we choose to model both channels as linear systems with input scaled to normalized actuator effort (\(\pm 1\)).

Surge channel. Input is normalized throttle; output is the body-fixed forward (surge) velocity \(v_x = \dot{x}\) (m/s):

\[G_{v_x}(s) = \frac{K_{v_x}}{\tau_{v_x}\, s + 1} \quad\text{(throttle} \to v_x\text{)}\]

Yaw channel. The model from steering effort (rudder deflection) to yaw angle \(\psi\) is second-order (the integrator comes from yaw rate accumulating into angle):

\[G_{\psi}(s) = \frac{K}{s\,(\tau\, s + 1)} \quad\text{(rudder} \to \psi\text{)}\]

For this lab we identify the first-order model from rudder to the yaw rate \(r = \dot{\psi}\) (not yaw angle):

\[G_r(s) = \frac{K_r}{\tau_r\, s + 1} \quad\text{(rudder} \to r\text{)}\]

Identifying on \(r\) instead of \(\psi\) gives a well-defined DC gain \(K_r\) (steady-state yaw rate per unit rudder command). The second-order “integrator” view is useful for intuition about controller structure (we’ll see that later).

Schedule

This week (field): Collect one clean open-loop step response for each channel. Repeat the step a few times during each arm-disarm cycle to make sure at least one trace is clean.

Next week (analysis + deliverable): process the logs with the provided MATLAB scripts, identify K and τ for each channel, overlay the simulated model on the data, and assemble the two-slide presentation.

Deliverable

One PowerPoint file per team, submitted via Sakai. Each team member submits a copy (shared source, individual submissions).

  • Title slide: team name and member names.
  • Slide 2 — Surge channel:
    • Final step response data plot (speed vs. time, correct units) with the simulated model overlaid.
    • Table with identified model parameters: \(K_{v_x}\), \(\tau_{v_x}\).
    • Transfer function expression: \(G_{v_x}(s) = \frac{K}{\tau s + 1}\) with the identified numbers filled in.
  • Slide 3 — Yaw-rate channel:
    • Same three elements as the surge slide, but for yaw rate vs. time.
    • Table with \(K_r\), \(\tau_r\).
    • Transfer function expression with identified numbers.

Template and an example will be shown in class.

For Students

  • Shared data repository: ME2801_USV_Shared — upload your team’s raw *.BIN autopilot logs to your team subfolder. Instructors will convert the logs to MATLAB .mat format.
  • Step-response visualization: proc_openloop_response.m — loads a .BIN.mat, plots surge and yaw step responses for visual inspection, saves a trimmed .BIN.proc.mat with the fields needed for sysid.
  • System identification: lab1_sysid_proto.m — MATLAB live script that loads a .proc.mat and performs the identification; the pattern to adapt to your own data.
  • Example dataset: step_resp_example.BIN.proc.mat — a known-good processed step-response dataset to develop and test your identification script against before you have your own data in hand.
  • Baseline parameters: 2026_05_06_baseline_3.2.param — the ArduRover parameter file loaded on the vehicle for all USV labs.
